`normalize(N)` is the most common call in any shader. Occasionally it returns `NaN` and a whole patch of the mesh goes black. By the end of this lesson you will know exactly what `normalize` computes, why it is Pythagoras in disguise, and which input makes it fail.

## 1. Length is Pythagoras

A vector $\mathbf{v} = (3, 4)$ is the hypotenuse of a right triangle with legs 3 and 4. Its length, written $\lvert \mathbf{v} \rvert$, is what [Pythagoras](lesson:pythagoras) gives:

$$
\lvert \mathbf{v} \rvert = \sqrt{3^2 + 4^2} = \sqrt{9 + 16} = \sqrt{25} = 5
$$

Draw a square on each leg: a 3-by-3 square of area 9 and a 4-by-4 square of area 16. Their areas add to 25, the square on the hypotenuse. The squared length $\lvert \mathbf{v} \rvert^2 = 25$ is a sum of areas; the length itself is the root.

{/* scene: 1.3-1 — Pythagoras tiles on each component; a timeline unfolds |v|² = Σ vᵢ² one component at a time as the running sum grows */}

In 3D we did Pythagoras twice in lesson 0.3 (floor diagonal first, then up), and the result was one formula with three squares. For $\mathbf{v} = (1, 1, 1)$:

$$
\lvert \mathbf{v} \rvert = \sqrt{1^2 + 1^2 + 1^2} = \sqrt{3} \approx 1.732
$$

Note that $\sqrt{3}$ is not 3. The length of $(1, 1)$ is $\sqrt{2} \approx 1.414$, not 2.

## 2. Σ notation: "add these up"

Writing $v_1^2 + v_2^2 + v_3^2 + \cdots + v_n^2$ gets old. Mathematicians compress "add this expression for $i$ from 1 to $n$" into one symbol:

$$
\sum_{i=1}^{n} v_i^2 = v_1^2 + v_2^2 + \cdots + v_n^2
$$

Read $\sum$ (capital sigma) as "sum of". The letter under it is the loop counter, the number above it is the last value, and the expression to the right is what gets added each time. It is literally a `for` loop with an accumulator. Python counts from 0, so `range(n)` runs $i = 0 \ldots n-1$ where $\sum$ writes $1 \ldots n$; same $n$ terms.

<PyCell>

```python
v = [3., 4.]
n = len(v)
total = 0.0
for i in range(n):
    total += v[i] ** 2
print(total, total ** 0.5)   # 25.0 5.0
```

</PyCell>

With it, the length of a vector with any number of components is one line:

$$
\lvert \mathbf{v} \rvert = \sqrt{\sum_{i=1}^{n} v_i^2}
$$

For $\mathbf{v} = (3, 4)$ this is $n = 2$: $\sqrt{9 + 16} = 5$. For $(1, 1, 1)$ it is $n = 3$: $\sqrt{3}$. For a vector of eight ones, $n = 8$: $\sqrt{8} \approx 2.83$. The formula does not care about the count.

## 3. Length in n dimensions

Here is an 8-component vector, $\mathbf{v} = (2, 1, 2, 0, 4, 0, 1, 2)$. There is no picture of it. Compute anyway:

$$
\sum v_i^2 = 4 + 1 + 4 + 0 + 16 + 0 + 1 + 4 = 30, \qquad \lvert \mathbf{v} \rvert = \sqrt{30} \approx 5.48
$$

That is the whole method. A 4096-dimensional embedding has a length in exactly this sense: square each component, add, take the root.

{/* scene: 1.3-3 — n-D: an 8-component bar chart; drag bars, the length readout updates: no picture needed, the same formula */}

Two facts that follow from the squares:

- $\lvert -\mathbf{v} \rvert = \lvert \mathbf{v} \rvert$. Flipping an arrow does not change its length, because $(-v_i)^2 = v_i^2$. Squares forget the sign (lesson 0.G).
- $\lvert s\,\mathbf{v} \rvert = \lvert s \rvert \cdot \lvert \mathbf{v} \rvert$. For a plain number, $\lvert s \rvert$ is its absolute value from lesson 0.G ($\lvert -2 \rvert = 2$), not a length. Scaling by 3 makes the arrow 3 times longer; scaling by $-2$ makes it 2 times longer and flips it. Check with $\mathbf{v} = (3, 4)$, $s = -2$: $(-6, -8)$ has length $\sqrt{36 + 64} = 10 = 2 \cdot 5$.

**Misconception to drop:** "$\lvert -\mathbf{v} \rvert = -\lvert \mathbf{v} \rvert$". Length is never negative. It is a root of a sum of squares.

## 4. Normalization: keep the direction, set the length to 1

A **unit vector** is a vector of length 1. To turn any non-zero vector into a unit vector pointing the same way, divide it by its own length:

$$
\hat{\mathbf{v}} = \frac{\mathbf{v}}{\lvert \mathbf{v} \rvert}
$$

This is scaling by the scalar $1 / \lvert \mathbf{v} \rvert$, so the direction is kept (section 2 of [lesson 1.2](lesson:vector-arithmetic)) and the new length is $\lvert \mathbf{v} \rvert / \lvert \mathbf{v} \rvert = 1$.

Example 1. $\mathbf{v} = (0, 5)$: length 5, so $\hat{\mathbf{v}} = (0/5,\; 5/5) = (0, 1)$.

Example 2. $\mathbf{v} = (1, 1)$: length $\sqrt{2} \approx 1.414$, so

$$
\hat{\mathbf{v}} = \left(\tfrac{1}{\sqrt 2},\; \tfrac{1}{\sqrt 2}\right) \approx (0.707,\; 0.707)
$$

Check exactly: $(1/\sqrt 2)^2 + (1/\sqrt 2)^2 = 1/2 + 1/2 = 1$ (with the rounded $0.707$ you get $0.4998 + 0.4998 \approx 1$). The tip lands on the unit circle from [lesson 0.4](lesson:unit-circle); in 3D it lands on the unit sphere.

Example 3. $\mathbf{v} = (3, 4)$: $\hat{\mathbf{v}} = (0.6, 0.8)$, and $0.36 + 0.64 = 1$.

{/* scene: 1.3-2 — scrub a blend from v to v/|v|; the tip lands on the unit circle (2D) or unit sphere (3D); the divisor |v| in the formula is highlighted */}

**Misconception to drop:** "normalizing changes the direction". It only changes the length. The arrow $(0.6, 0.8)$ points exactly where $(3, 4)$ points.

**The one input that fails.** The zero vector $(0, 0, 0)$ has length 0. Dividing by 0 gives `NaN` (or infinity), and there is no direction to keep anyway: the zero arrow does not point anywhere. This is the black patch in your shader: a degenerate triangle produced a zero-length normal, `normalize` divided by zero, and every pixel lit with that normal became `NaN`. Every robust `normalize` checks for a tiny length first.

**Length versus length squared.** Comparing two lengths does not need the root: $\lvert \mathbf{a} \rvert < \lvert \mathbf{b} \rvert$ exactly when $\lvert \mathbf{a} \rvert^2 < \lvert \mathbf{b} \rvert^2$, because squaring keeps the order of non-negative numbers. CG code therefore compares `length2(v) < r*r` and skips the square root (lesson 0.G named this; here is where it pays).

> **Say it simpler.** Length = Pythagoras with as many legs as there are components. Normalizing = keep the direction, make the length 1. You cannot normalize nothing.

## Python

`np.linalg.norm` is the length. Normalizing is dividing by it. Watch the last line: in floating point the normalized length is often `0.9999999...` rather than exactly `1.0`, because $1/\sqrt{2}$ cannot be stored exactly. Compare with a tolerance, never with `==`.

<PyCell>

```python
import numpy as np

v = np.array([3., 4.])
print(np.linalg.norm(v))                 # 5.0
print(np.sqrt((v**2).sum()))             # 5.0   the same, by hand (Sigma notation)

ones8 = np.ones(8)
print(np.linalg.norm(ones8))             # 2.8284271247461903 = sqrt(8)

v_hat = v / np.linalg.norm(v)
print(v_hat)                             # [0.6 0.8]
print(np.linalg.norm(v_hat))             # 1.0

w = np.array([1., 1.])
w_hat = w / np.linalg.norm(w)
print(w_hat, np.linalg.norm(w_hat))      # [0.70710678 0.70710678] 0.9999999999999999
print(np.isclose(np.linalg.norm(w_hat), 1.0))   # True: compare with a tolerance

# the failure case
z = np.zeros(3)
with np.errstate(invalid='ignore'):
    print(z / np.linalg.norm(z))         # [nan nan nan]

def safe_normalize(v, eps=1e-12):
    n = np.linalg.norm(v)
    return v / n if n > eps else np.zeros_like(v)
print(safe_normalize(z))                 # [0. 0. 0.]
```

</PyCell>

<details>
<summary>Machine layer: rsqrt, epsilon and fp16</summary>

Hardware normalizes as `v * rsqrt(dot(v, v))`: the reciprocal square root (`rsqrtss` on x86, `inversesqrt` in GLSL) is one fast instruction and one multiply replaces a division. The epsilon guard above is what every engine's `normalize` does, sometimes silently returning zero.

A second trap matters for AI. Half precision (`fp16`) cannot store numbers above 65 504. Take a vector of 100 components each about 30: every square is about 900 and the sum of squares is about 90 000, which overflows to infinity before the root is even taken. That is why norms, and LayerNorm in a network, are accumulated in `fp32` even when the weights are stored in `fp16`. This thread continues into the number-formats branch at the end of the course.

</details>

## What this opens

We can measure how long any arrow is. Two arrows, though, also have an *angle* between them, and we have no way to compute it from components yet. The [law of cosines](lesson:law-of-cosines) from Part 0 already relates the sides of a triangle to its angle; combining it with lengths gives a new operation: [the dot product](lesson:dot-product).
