**Опирается на:** [Что такое тензор](lesson:tensor-road) · [Данные как тензоры](lesson:data-as-tensors).

Это машинный уровень любой тензорной библиотеки. В [дороге тензоров](lesson:tensor-road) вы видели, что тензор хранится
одной плоской лентой и читается через **шаги**. Здесь мы понимаем это буквально: тензор — это указатель на буфер плюс
три вещи, и почти любая «операция» над его формой переписывает только эти три вещи.

## Тензор = буфер + форма + шаги + смещение

- **Буфер**: одна строка чисел в памяти, адреса 0, 1, 2, …
- **Форма**: размер каждой оси, $(2, 3, 4)$.
- **Шаги** (strides): на сколько адресов прыгает один шаг вдоль каждой оси, $(12, 4, 1)$.
- **Смещение** (offset): адрес первой ячейки, `x[0, 0, 0]`. Обычно 0.

Адрес любой ячейки — это смещение $o$ плюс каждый индекс $i$, умноженный на свой шаг $s$:

$$
a = o + i_0 s_0 + i_1 s_1 + i_2 s_2
$$

Для `x[1, 2, 3]` в обычной раскладке: $a = 0 + 1 \cdot 12 + 2 \cdot 4 + 3 \cdot 1 = 23$. Больше тензорная библиотека
ничего не делает, чтобы найти число. На языке CG это то, как шейдер находит тексель $(u, v)$ в текстуре: строка,
умноженная на шаг строки, плюс столбец, умноженный на байты на тексель.

В карточке ниже `x` — это `np.arange(24)`: буфер хранит числа от 0 до 23, поэтому **каждое число — ещё и свой
собственный адрес**. Какое бы представление вы ни построили, число на ячейке говорит, где в памяти она живёт.

## Представления: новые числа, та же память

Выберите представление под карточкой. Вверху карточки — `y` в собственной форме; под ним — буфер x. Щёлкните ячейку
`y`: пунктир уходит вниз к адресу, который она читает, а строка под карточкой расписывает сумму. Ячейки буфера, которые
`y` никогда не читает, бледнеют, а маленькие числа в ленте показывают, в каком порядке их посещает обход `y` по строкам.

При `x` формы $(2, 3, 4)$ с шагами $(12, 4, 1)$ каждое представление ниже получается изменением одних только чисел:

| представление | форма | шаги | смещение | что изменилось |
|---|---|---|---|---|
| `x.T` | $(4, 3, 2)$ | $(1, 4, 12)$ | 0 | оси и шаги перевёрнуты |
| `x[..., ::2]` | $(2, 3, 2)$ | $(12, 4, 2)$ | 0 | каждый второй столбец: этот шаг удваивается |
| `x[::-1]` | $(2, 3, 4)$ | $(-12, 4, 1)$ | 12 | первая ось задом наперёд: отрицательный шаг, старт с листа 1 |
| `x[1]` | $(3, 4)$ | $(4, 1)$ | 12 | целый индекс убирает ось и сдвигает смещение |
| `x[..., 1:3]` | $(2, 3, 2)$ | $(12, 4, 1)$ | 1 | обрезка: размеры меньше, старт на один столбец правее |

Проверим одно: в `x[::-1]` ячейка `y[0, 0, 0]` лежит по адресу $12 + 0 = 12$, а `y[1, 0, 0]` — по адресу $12 - 12 = 0$.
Чтение первой оси задом наперёд — это правда всего лишь шаг $-12$.

**Представление** делит буфер. Запись в `y` меняет `x`. Это цена бесплатности.

## Непрерывность, reshape и единственная копия

Тензор **непрерывный**, когда его обход по строкам читает буфер по порядку, $0, 1, 2, \dots$ без дыр и без прыжков:
последний шаг равен 1, а каждый шаг перед ним равен произведению размеров после него. `x` непрерывный; `x.T`,
`x[..., ::2]` и `x[::-1]` — нет.

**Reshape** перечитывает те же числа в том же порядке с новой формой. Для непрерывного тензора это просто новые шаги:
$(2, 3, 4) \to (2, 12)$ даёт шаги $(12, 1)$ — представление. Для тензора, который не непрерывен, может вообще не
найтись шагов, читающих его ячейки в новом порядке. В модели этого урока reshape тогда **отказывает**, и копию нужно
сделать самому. (Библиотеки различаются: `view()` в PyTorch отказывает так же, `reshape` в NumPy молча копирует, и обе
иногда всё-таки находят шаги для особых не непрерывных случаев.)

Копия — это `contiguous()` (PyTorch) или `np.ascontiguousarray` (NumPy). Она обходит представление по строкам и
записывает ячейки в **новый буфер** в этом порядке. Попробуйте в карточке: начните с `x.T`, попросите
`.reshape(2, -1)`, прочитайте отказ, затем отметьте **contiguous()**. Появится вторая лента: новый буфер хранит
$0, 12, 4, 16, 8, 20, 1, \dots$, и теперь reshape — обычное представление этого буфера. Если тензор уже непрерывный,
`contiguous()` возвращает его без изменений: без копии, тот же буфер.

Итак, операций ровно два вида:

- **представления** (reshape непрерывных данных, транспонирование, срезы, добавление или удаление оси размера 1):
  новые форма, шаги и смещение, работа $O(1)$, общая память;
- **копии** (`contiguous`, reshape, которому она нужна, большая часть арифметики): новый буфер, работа
  пропорциональна размеру.

## По строкам и по столбцам

«По строкам» (row-major, порядок C) значит, что быстрее всех меняется последний индекс. «По столбцам» (column-major,
порядок Fortran) — что быстрее всех меняется **первый** индекс: шаги $(1, 2, 6)$ для формы $(2, 3, 4)$. NumPy и
PyTorch по умолчанию хранят по строкам; Fortran, MATLAB, Eigen (по умолчанию) и матричные uniform-переменные OpenGL —
по столбцам.

Отметьте **x по столбцам** в карточке. Те же 24 числа теперь лежат в другом порядке, и вот классическая ошибка CG на
одной картинке: транспонированный массив, хранимый по столбцам, — это массив, хранимый по строкам. Выберите `x.T`, и
результат снова непрерывен. Матрица $4 \times 4$, записанная одной библиотекой и прочитанная другой с противоположным
соглашением, приезжает транспонированной.

## Почему порядок обхода важен для скорости

Память приходит не по одному числу. Процессор приносит целую **строку кэша**: 64 байта на нынешних процессорах x86
от Intel и AMD (128 байт на Apple M-серии), то есть 16 чисел `float32` сразу. Прочитать остальные 15 после этого почти
ничего не стоит; принести новую строку из оперативной памяти — примерно в сто раз дольше, чем прочитать из ближайшего
кэша.

Карточка обходит матрицу $16 \times 16$ из `float32`. Одна строка матрицы — это $16 \cdot 4 = 64$ байта, ровно одна
строка кэша. Игрушечный кэш справа держит несколько строк и выбрасывает ту, что дольше всех не использовалась, когда
приходит новая.

При обходе по строкам каждая строка кэша приносится один раз и затем используется 16 раз: 16 промахов на 256 чисел
при любом размере кэша. При обходе по столбцам каждый шаг попадает в другую строку, поэтому с кэшем в 4 строки каждый
шаг — промах: 256 промахов, в 16 раз больше обмена с памятью ради тех же 256 чисел. Спасает обход по столбцам только
кэш, вмещающий всю матрицу, а настоящие тензоры гораздо больше любого кэша.

У GPU то же правило в другой форме. Варп из 32 потоков читает память вместе, и железо обслуживает его 32-байтовыми
транзакциями: когда поток $k$ читает $k$-е подряд идущее `float32`, четыре транзакции обслуживают все 32 потока. С
шагом 2 половина каждой транзакции пропадает (эффективность 50 %), а при больших шагах каждому потоку нужна своя
транзакция: 32 штуки (NVIDIA, *CUDA C++ Best Practices Guide*, раздел 10.2.1 «Coalesced Access to Global Memory»,
проверено 2026-10-11).

Поэтому библиотеки зовут `contiguous()` перед тяжёлыми ядрами, поэтому транспонирование бесплатно, а умножение матриц
после него — не обязательно, и поэтому порядок осей ($B \times H \times W \times C$ или $B \times C \times H \times W$)
выбирают под железо.

## Вручную

1. Форма $(4, 5)$, по строкам. Шаги? Адрес `x[3, 2]`?
2. Тот же `x`, транспонированный. Форма и шаги? Какой адрес читает `x.T[2, 3]`?
3. `x[::-1]` для формы $(4, 5)$: шаги и смещение?
4. Можно ли `x.T` (форма $(5, 4)$) переделать в $(20,)$ без копии? Почему?
5. Форма $(2, 3, 4)$, по столбцам: шаги и адрес `x[1, 2, 3]`?

<details>
<summary>Ответы</summary>

1. Шаги $(5, 1)$; $3 \cdot 5 + 2 = 17$.
2. Форма $(5, 4)$, шаги $(1, 5)$; $2 \cdot 1 + 3 \cdot 5 = 17$: та же ячейка, конечно.
3. Шаги $(-5, 1)$, смещение $3 \cdot 5 = 15$ (первая прочитанная ячейка — начало последней строки).
4. Нет: его обход по строкам читает адреса $0, 5, 10, 15, 1, 6, \dots$, и никакой один шаг этого не даст. Сначала нужна
   копия (`contiguous()`).
5. Шаги $(1, 2, 6)$; $1 + 2 \cdot 2 + 3 \cdot 6 = 23$.

</details>

## В NumPy

<PyCell>

```python
import numpy as np

x = np.arange(24, dtype=np.int64).reshape(2, 3, 4)
print(x.strides, x.itemsize)                         # (96, 32, 8) 8: strides in bytes

y = x.T                                              # a view: shape and strides reversed
print(y.shape, y.strides, np.shares_memory(x, y))    # (4, 3, 2) (8, 32, 96) True
print(y.flags['C_CONTIGUOUS'])                       # False

s = x[..., ::2]                                      # every second column: that stride doubles
print(s.shape, s.strides)                            # (2, 3, 2) (96, 32, 16)
r = x[::-1]                                          # the first axis backwards: a negative stride
print(r.strides, r[0, 0, 0])                         # (-96, 32, 8) 12

z = np.ascontiguousarray(y)                          # the copy, written in y's walk order
print(z.ravel()[:6], np.shares_memory(z, x))         # [ 0 12  4 16  8 20] False
print(z.reshape(2, -1).base is z)                    # True: this reshape is a view of z
w = y.reshape(2, -1)                                 # NumPy copies here without saying so
print(np.shares_memory(w, x))                        # False

f = np.arange(24, dtype=np.int64).reshape((2, 3, 4), order='F')
print(f.strides, f.T.flags['C_CONTIGUOUS'])          # (8, 16, 48) True
```

</PyCell>

NumPy считает шаги в **байтах** ($96 = 12 \cdot 8$ для `int64`); `x.stride()` в PyTorch считает элементы, как этот
урок.

## Что дальше

Теперь вы знаете, сколько стоит тензор: представления бесплатны, копии — нет, а порядок обхода решает, какая часть
каждой принесённой строки кэша пойдёт в дело. Следующие уроки считают целыми тензорами: поэлементные операции и
broadcasting (представление с шагом 0), затем редукции, которые схлопывают ось.
